# Experiment 02 — serve a ported animation from the game's own archive

**Settles:** decision 25, and an open `BACKLOG.md` item asking whether a share can resolve a
vanilla source path at all. Also decides whether the builder's manifest can resolve `ship` versus
`share` per move.

**Status: prepared, NOT applied.** It modifies `pikachu-moveset/mod/`, which another session is
actively building and deploying from. Do not apply while that is running.

## The two files, and why only two

Measured: of the 74 animations the mod ships, exactly **two** are byte-identical to their vanilla
source.

| file | source | bytes |
|---|---|---|
| `c00attack11.nuanmb` | `chrom` | 42,872 |
| `g02cliffattack.nuanmb` | `ganon` | 57,888 |

The other 72 carry two edits — foreign bone- and mesh-track trimming, and the `Rot` scale multiply
by `source_scale / 0.96` — and **you cannot apply an edit to bytes you do not ship.**

These two are clean for a computable reason, not by luck: `chrom`, `ganon` and `pikachu` are all
scale **0.9600**, so the multiply is exactly 1.0, and neither animation touches a bone or mesh
Pikachu lacks, so trimming had nothing to drop. That gives the builder its predicate:

> **share when `source_scale == host_scale` and the animation's track set is a subset of the
> host's bones and meshes** — both decidable offline from `tools/scales.tsv`, the host skeleton,
> and the animation's own track list.

For Pikachu, 10 fighters share 0.9600. Roster-wide the modal scale is 1.0000 with 38 fighters, so
for a typical host the same-scale candidate set is large.

## The patch

1. Delete from the mod tree:
   ```
   pikachu-moveset/mod/fighter/pikachu/motion/body/c00/c00attack11.nuanmb
   pikachu-moveset/mod/fighter/pikachu/motion/body/c00/g02cliffattack.nuanmb
   ```
2. Add to `config.json` — **`share-to-vanilla`**, not `share-to-added`, because both target paths
   already exist in vanilla Pikachu (27,360 and 37,088 bytes respectively):
   ```json
   "share-to-vanilla": {
     "fighter/chrom/motion/body/c00/c00attack11.nuanmb":
       ["fighter/pikachu/motion/body/c00/c00attack11.nuanmb"],
     "fighter/ganon/motion/body/c00/g02cliffattack.nuanmb":
       ["fighter/pikachu/motion/body/c00/g02cliffattack.nuanmb"]
   }
   ```
3. `config.json` is generated by `tools/gen-config.sh`, so the entries belong in its hand-declared
   `ALIASES` block rather than in the output file — otherwise the next build erases them.

## Why this is the interesting branch

The three Chrom sword **textures** the mod already shares go through ARCropolis's
`add_shared_file`, because their target paths are new. A target that **already exists in vanilla**
takes a different branch, `reshare_file`, and this project has never run it. So the experiment
tests a code path, not just a config key.

## What to look for

Both moves are ones you have played many times, and a correct result is **indistinguishable from
the current build** — which is exactly why these two files were chosen.

| outcome | meaning |
|---|---|
| jab and ledge attack look and behave unchanged | sharing works; the predicate is usable and the builder can stop shipping same-scale animations |
| either move plays Pikachu's own animation instead | the share did not resolve; the mod tree is now missing a file it needs |
| the move plays nothing, or the fighter T-poses | the motion resolved to an empty or absent file |

Three instruments read it with no new code: the in-game self-test's RESOLVED line for `attack_11`,
`sd:/ultimate/arcropolis/conflicts.json`, and the Skyline log — whose relevant failure strings are
already known from the 4.0.9 binary:

```
Failed to find file '…' when attempting to share file to it.
Could not get shared file for file '…' when attempting to reshare it.
```

## Reverting

`git checkout` the two `.nuanmb` files and the `ALIASES` block, rebuild, redeploy. Nothing else in
the mod changes.
